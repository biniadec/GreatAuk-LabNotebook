Getting Started on Mjolnir

Before you touch any genomic data, you need to be comfortable working independently on Mjolnir, the University of Copenhagen's HPC cluster. This module covers the HPC and Linux fundamentals — connecting, navigating, storage, software, and Slurm — that every later module assumes you already have. Everything here recurs constantly from Module 01 onward, so it's worth doing properly now rather than guessing later.

Learning objectives

  • Connect to Mjolnir and tell the difference between a login node and a compute node
  • Navigate the filesystem confidently, and understand absolute vs relative paths
  • Know where your files belong on Mjolnir (home vs project storage) and how to check usage
  • Use basic file operations safely: cp, mv, rm, head, less, cat, file
  • Find and load shared software using environment modules
  • Understand what Slurm is, and why jobs must request resources
  • Write, submit, and monitor a Slurm batch job
  • Read a job's output/error files, and check how efficiently it used its resources
  • Cancel a job, and know when that's appropriate

Connect to Mjolnir and identify yourself

✓ Complete
Concept

Mjolnir access goes through the UCPH VPN, then SSH with your KU ID. Logging in doesn't put you on the machine that runs analyses — it puts you on a shared login node. The first habit to build, every single session, is confirming who you are and where you've landed before doing anything else.

Task

Connect to Mjolnir, then run three commands: one that prints your username, one that prints the machine's name, and one that prints your current location.

Hint

The connection itself is one SSH command using your KU ID. Once in, whoami, hostname, and pwd each answer one of the three questions above.

Show command
# from your own computer, with the UCPH VPN connected ssh <KU-ID>@mjolnirgate.unicph.domain # once logged in whoami hostname pwd

whoami prints your username (it should match your KU-ID). hostname prints the machine's name — on Mjolnir this confirms you're on a login node. pwd prints your current absolute path.

Check yourself

Does whoami match your KU-ID? What command or piece of information would you use to confirm which machine/node you are currently on?

02

What is an HPC cluster, and what is Mjolnir?

✓ Complete
Concept

An HPC (High-Performance Computing) cluster is many networked computers sharing storage and a scheduler, pooled together so jobs too large for a single laptop — and jobs from many people at once — can run efficiently. Mjolnir is UCPH's cluster for exactly this kind of research. Crucially, you are never the only person using it: everything about how you're expected to behave on it (which you'll meet across this module) follows from that one fact.

Task

In your own words, write a short note explaining what makes a cluster different from your own laptop, and why sharing it with many other researchers changes how you're expected to use it.

Hint

Think about what would happen if every user on a shared machine ran heavy, long-running work wherever and whenever they liked.

Show model answer

A cluster multiplies the compute and memory available to you far beyond a laptop, but that capacity is finite and shared. If one person's job eats all the CPU or memory on a shared entry point, every other person connected at that moment is slowed down — so clusters enforce etiquette (separate login/compute nodes, a scheduler, resource limits) that a single-user laptop never needs.

Check yourself

Can you name one concrete rule a shared cluster needs that your own laptop never would?

03

Login nodes vs compute nodes: what belongs where

✓ Complete
Concept

Mjolnir's login node is a shared entry point for everyone connected at that moment — meant for lightweight tasks: organising files, writing scripts, submitting and checking jobs. Actual analyses run on compute nodes, scheduled through Slurm. Running real computation on the login node slows down every other user's session, and persistent misuse can lead to your access being withdrawn.

Task

List three tasks that belong on a login node, and three that must go to a compute node instead. Think ahead to the kind of work you'll do in later modules (downloading a small reference file vs. running an alignment, for example).

Hint

The deciding factor isn't "is this a command I type" — it's how much CPU, memory, or time it's likely to need.

Show model answer

Login node: editing a script, organising directories, checking a small file with head, submitting a job with sbatch.

Compute node (via Slurm): aligning reads to a genome, running an assembly, anything described as "model training," or any step whose runtime or memory you genuinely aren't sure of in advance.

Check yourself

What do you think actually happens — technically and socially — if everyone treated the login node like a compute node?

These four commands are the absolute foundation of working on any Linux server, and you'll run them more than anything else in this entire project: pwd (where am I), ls (what's here), ls -lh (the same, with detail and readable sizes), and cd (go there).

05

Shortcuts that matter: ., .., ~

✓ Complete
Concept

. means "this directory," .. means "the parent directory," and ~ means "my home directory" — all three save you from typing full paths constantly, and all three appear again and again in other commands, not just cd.

Task

From wherever you currently are, jump straight home, then move up one level from there, then return to exactly where you started using the shortcut, not a typed-out path.

Hint

cd ~ works from anywhere. cd - is a bonus shortcut that returns you to wherever you were before your last cd.

Show command
cd ~ pwd cd .. pwd cd - pwd
Check yourself

Where might . be useful as an argument to a command other than cd — for example, as a destination for cp?

06

Absolute vs relative paths

✓ Complete
Concept

An absolute path starts from the root of the filesystem (/) and is unambiguous no matter where you currently are. A relative path is interpreted relative to your current directory — shorter to type, but it only means what you think it means if you know your starting point. Mixing these up is one of the most common sources of "file not found" errors, and worse, scripts that silently touch the wrong location.

Task

Print the absolute path of your home directory without moving there. Then, from a subdirectory of your choice, write down a relative path that points back to that same home directory.

Hint

echo ~ expands and prints your home directory's absolute path without changing your location. An absolute path always starts with /; a relative one never does.

Show command
echo ~ cd <some_subdirectory> pwd # relative path back to where you started cd ..
Check yourself

If you moved to a completely different directory first, would the same relative path (e.g. ../data) still point to the same place? Why not — and why does an absolute path not have this problem?

07

Home vs project storage on Mjolnir

✓ Complete
Concept

Your home directory (/home/<KU-ID>) is personal but capped at 100 GB, and is meant for configuration files and small scripts — not datasets or analysis output. Actual project data belongs under /projects/<project>/, which has a standard layout: people/<KU-ID>/ (your own working space), data/ (shared datasets used by the whole project), and scratch/ (temporary working space — not backed up, so treat anything there as disposable). If your people/ folder doesn't exist for you yet, ask your supervisor or Mjolnir support rather than improvising a location yourself.

Task

Find both locations: your home directory, and your personal folder within the project's shared space. Don't create anything yet — just confirm both exist and note the difference.

Hint

echo ~ gives you the first. The second has the shape /projects/<project>/people/<KU-ID>/ — ls /projects/ shows you which projects you can see.

Show command
echo ~ ls /projects/ ls /projects/<project>/people/

Replace <project> with the actual project name your supervisor gives you.

Check yourself

Which of these two locations should hold your actual working files for this course, and why?

09

Checking your storage usage

✓ Complete
Concept

/projects/ storage isn't currently quota-enforced the way your home directory is — but it's still a shared, finite resource used by many research groups, not an unlimited personal allocation. Checking usage periodically is good practice, not a one-off task.

Task

Check how much space your personal project folder is using, and which subfolders (if any) are using the most.

Hint

The flag that matters for accurate reporting is --apparent-size — it reports actual data size rather than filesystem allocation, which is what you want for capacity planning.

Show command
# total usage du -sh --apparent-size /projects/<project>/people/<KU-ID>/ # broken down by immediate subfolder, smallest to largest du -h --apparent-size --max-depth=1 /projects/<project>/people/<KU-ID>/ | sort -h
Check yourself

Does the first command give you one total? What does the second one show you that the first doesn't?

10

Copying, moving, and (carefully) removing files

✓ Complete
Concept

cp copies a file, leaving the original in place. mv moves it — or renames it, since there's no separate "rename" command. rm deletes a file permanently: there is no undo and no recycle bin, so always double-check the path (and any wildcard) before pressing enter.

Task

Create a small text file, make a copy of it, rename that copy, then delete the renamed copy — leaving the original untouched.

Hint

echo "some text" > filename writes that text into a new file. mv used with a new name in the same directory renames a file.

Show command
echo 'hello world' > notes.txt cp notes.txt notes_backup.txt mv notes_backup.txt notes_copy.txt rm notes_copy.txt ls -lh
Check yourself

Is notes_copy.txt recoverable after rm? Does notes.txt still exist? What's one habit worth building before running rm, especially with a wildcard like *?

11

Inspecting files without fully opening them

✓ Complete
Concept

Files on a cluster can be huge — opening one fully is slow at best, and can freeze your session at worst. cat prints a whole (small) file. head prints just the start. less lets you page through interactively without loading everything at once. file reports what a file actually is, regardless of its extension.

Task

Using the notes.txt file from the previous exercise, try all four commands.

Hint

less is interactive — press q to quit back to the prompt.

Show command
cat notes.txt head -n 5 notes.txt less notes.txt file notes.txt
Check yourself

What does file report for this plain text file? You'll see it report something very different — "gzip compressed data" — once you start working with real genomic files in Module 01. Why is checking this before you assume a file's format a good habit?

12

What are environment modules, and why do they exist?

✓ Complete
Concept

Mjolnir provides shared research software through Environment Modules. Rather than everyone installing their own copy of every bioinformatics tool, pre-installed software is loaded into your shell's (or job's) environment on demand with a single command. Much of it is packaged internally as Conda environments, but you access it through the module system, not by managing Conda yourself.

Task

Before touching any commands, think about and note down: why would a shared cluster prefer this system over letting every user install and manage their own software?

Hint

Think about disk space (your home directory's 100 GB cap), reproducibility, and what happens if 50 people each install a slightly different version of the same tool.

Show model answer

Shared, version-pinned installs save enormous duplicated disk space and effort, and mean that when you tell someone which module (and version) you used, they can reproduce your environment exactly — rather than everyone's personal installs silently drifting apart.

Check yourself

Why might installing your own Conda environment in your home directory specifically be a bad idea on Mjolnir?

13

Finding and loading software

✓ Complete
Concept

module avail lists everything installed; adding a search term narrows it. module whatis and module display show details before you commit to loading something. module load brings a tool into your environment — pin an exact version for work you intend to repeat. module list shows what's currently loaded, and module purge clears everything.

Modules required by a batch job must be loaded inside the sbatch script itself — a batch job starts in its own environment on a different machine, so anything you loaded interactively in your login shell does not carry over.

Note: Mjolnir does not support module spider, even though you may see it mentioned elsewhere — use module avail and module apropos instead.

Task

Search for samtools (a very common bioinformatics tool you'll likely use later), check what versions exist, load one, confirm it's active, then clear your environment again.

Hint

which samtools confirms a loaded tool is actually on your PATH.

Show command
module avail samtools module apropos samtools module whatis samtools module load samtools/<version> module list which samtools module purge

Replace <version> with one of the versions module avail samtools actually showed you — exact versions change over time, so don't assume one from elsewhere.

Check yourself

What does module list show immediately after module purge? Why might it be good practice to start every batch script with module purge before loading what you actually need?

14

What is Slurm, and why must you request resources?

✓ Complete
Concept

Slurm is the scheduler that decides which job runs on which compute node, and when. Every submitted job gets a job ID, and must declare the CPU, memory, and maximum wall time it needs, plus which partition (a pool of nodes for a particular purpose) and QoS (quality of service — a priority/limits tier) it should run under. On Mjolnir, --qos is mandatory: jobs submitted without one are rejected outright. cpuqueue is the general-purpose default partition; normal is the everyday default QoS. Mjolnir also has other partitions and QoS tiers for other situations (GPU work, low-priority background jobs, and more) — cpuqueue/normal is simply the everyday default you'll use for now.

Task

Before writing any script, note down: why does a shared cluster require everyone to declare their resource needs upfront, rather than just letting jobs run and seeing what happens?

Hint

Think about what information the scheduler needs to fit many users' jobs onto a limited number of machines without conflicts.

Show model answer

Without declared requirements, Slurm would have no way to know which jobs can safely run together on the same node without running out of memory or starving each other of CPU. Declared requests are also what Mjolnir's fairshare system charges against — more on that in Exercise 19.

Check yourself

What do you think happens if you request far more memory than your program actually ends up using? Hold that thought for Exercise 19.

15

Write your first Slurm batch script

✓ Complete
Concept

A Slurm batch script is an ordinary bash script with #SBATCH comment lines at the top telling Slurm what resources and settings to use before your actual commands run. --output/--error with %j let Slurm substitute the real job ID into the log filenames once it's submitted.

Task

Create a file called hello_mjolnir.sbatch that requests the minimum sensible resources for a job that only prints a hostname, a date, and a message — then prints that message.

Hint

A job that just runs hostname/date/echo needs barely any CPU, memory, or time — resist the urge to request more "just in case." You can create a multi-line file directly from the command line with a cat <<'EOF' ... EOF block, or use a terminal editor like nano if you prefer.

Show command
cat > hello_mjolnir.sbatch <<'EOF' #!/bin/bash #SBATCH --job-name=hello_mjolnir #SBATCH --partition=cpuqueue #SBATCH --qos=normal #SBATCH --nodes=1 #SBATCH --cpus-per-task=1 #SBATCH --mem-per-cpu=500M #SBATCH --time=00:05:00 #SBATCH --output=hello_mjolnir-%j.out #SBATCH --error=hello_mjolnir-%j.err echo "Starting job $SLURM_JOB_ID on $(hostname)" date echo "Hello from Mjolnir!" EOF cat hello_mjolnir.sbatch

--partition=cpuqueue is the general-purpose default. --qos=normal is mandatory and is the everyday default tier. --cpus-per-task=1 and --mem-per-cpu=500M are deliberately minimal, since this job only prints text. --time=00:05:00 is a safety cap, not an estimate of how long it'll actually take.

Check yourself

Why is requesting 1 CPU and 500 MB the right call here, compared to a heavier example you might see elsewhere in the documentation (e.g. 4 CPUs and 2 GB per CPU)?

17

Monitor your job

✓ Complete
Concept

squeue -u $USER shows your own queued and running jobs. A job's state (column ST) moves through PD (pending), R (running), CG (completing), and finally disappears from this live view once it's COMPLETED (or FAILED/TIMEOUT/CANCELLED).

Task

Run squeue -u $USER a few times, quickly — your job only takes seconds, so you're watching for it to appear running and then disappear.

Hint

While it's running, the last column of squeue's output shows the compute node's name. While pending, it shows the reason it's waiting instead.

Show command
squeue -u $USER
Check yourself

Which compute node did your job run on, according to squeue? Write it down — the final challenge will ask you to confirm this a different way.

18

Find and read your job's output and error files

✓ Complete
Concept

Because your script set --output/--error with %j, Slurm wrote two files named after your job ID. Normal output (like echo and date) goes to the .out file; errors and warnings go to the .err file. Telling these apart matters hugely once you're running real bioinformatics tools that report problems this way.

Task

List your directory, find the two log files matching your job ID, and inspect both.

Hint

A wildcard with your job ID will match both files at once in ls.

Show command
ls -lh *<jobid>* cat hello_mjolnir-<jobid>.out cat hello_mjolnir-<jobid>.err
Check yourself

Does the hostname printed inside the .out file match the compute node name squeue showed you? Is the .err file empty — what would you expect to see there if something had gone wrong?

19

Check how efficiently your job used its resources

✓ Complete
Concept

seff <jobid> gives a quick summary of CPU and memory use as a percentage of what you requested. sacct gives more detail. Right-sizing requests matters for reasons beyond your own job: fairshare is charged on what you request, not what you consume, so over-requesting hurts your own future priority; memory you reserve but don't use is unavailable to anyone else for the whole run, even while the CPUs sit idle; and smaller, realistic requests let the scheduler backfill jobs into gaps far more easily.

Task

Check your finished job's efficiency, and compare what you requested against what it actually used.

Hint

Both commands take your job ID as an argument.

Show command
seff <jobid> sacct -j <jobid> --format=JobID,JobName,State,Elapsed,AllocCPUS,ReqMem,MaxRSS,ExitCode
Check yourself

Did your job use anywhere near the 1 CPU / 500 MB you requested? If you'd requested 8 CPUs and 16 GB "just to be safe" instead, what would that have cost — to you and to everyone else sharing Mjolnir right now?

20

Cancelling a job

✓ Complete
Concept

scancel <jobid> requests termination — it doesn't guarantee an instant stop. Running jobs get a brief grace period before being forced to stop; pending jobs are simply removed from the queue. Appropriate reasons to cancel include wrong input files or arguments, wrong resource requests, an accidental duplicate submission, or a job that's clearly stuck. Repeatedly cancelling and resubmitting to try to "jump the queue" doesn't work — fairshare priority isn't affected by that.

Task

Submit a second, deliberately slow test job (one that just sleeps for a while), then cancel it before it finishes.

Hint

This needs its own script and its own job ID — your first job already finished, so there's nothing left to cancel there.

Show command
cat > sleep_test.sbatch <<'EOF' #!/bin/bash #SBATCH --job-name=sleep_test #SBATCH --partition=cpuqueue #SBATCH --qos=normal #SBATCH --nodes=1 #SBATCH --cpus-per-task=1 #SBATCH --mem-per-cpu=500M #SBATCH --time=00:10:00 #SBATCH --output=sleep_test-%j.out #SBATCH --error=sleep_test-%j.err sleep 600 EOF sbatch sleep_test.sbatch squeue -u $USER # cancel it using the job ID squeue just showed you scancel <jobid> squeue -u $USER
Check yourself

After running scancel, how long did it take for the job to actually disappear from squeue? Was it instant?
