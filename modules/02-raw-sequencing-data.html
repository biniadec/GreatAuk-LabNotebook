Module 02 of 10

Raw Sequencing Data

Modules 00 and 01 got you onto Mjolnir and gave you a reference genome. This module is about understanding what the Great Auk's own sequencing data actually are before you do anything to them. The raw data for this project are real, public, and hosted on ENA (the European Nucleotide Archive) — you'll work with the actual accessions throughout, not a generic stand-in dataset.

You will not run quality control, trimming, or mapping in this module — those belong to Modules 03 onward. By the end here, you should know exactly what you have, where it came from, how its pieces relate to each other, and that the files you've downloaded are intact. Nothing about the reads themselves will have changed.

Learning objectives

  • Trace the path from a museum specimen to the FASTQ files you'll actually work with
  • Explain what a sequencing library is, and why one specimen can have several
  • Distinguish specimen, sample, library/experiment, and run — using ENA's own terms
  • Read and interpret FASTQ structure and Phred quality, conceptually
  • Determine whether a real dataset is paired-end or single-end, rather than assume
  • Navigate the real Great Auk ENA record and build a table of its actual metadata
  • Distinguish what the metadata does and doesn't tell you about why several libraries exist
  • Download the real data reproducibly, verify it, and document its provenance

01

From ancient specimen to sequencing reads

✓ Complete
Concept

You already know the molecular biology — this is a refresher focused on the steps that matter once you're sitting in front of a terminal rather than a bench:

Museum specimen (bone, skin, tissue)
↓
DNA extraction — degraded, fragmented, chemically damaged DNA, vastly outnumbered by microbial/environmental DNA
↓
Library preparation — the extract is converted into a sequencer-ready pool of adapter-ligated molecules
↓
Sequencing — the library is loaded onto an instrument
↓
Base calling — raw signal becomes nucleotide calls with confidence scores
↓
FASTQ files — what you actually receive and work with
Task

Before continuing, note in your own words: which of these steps do you think determines how short and how damaged the DNA fragments end up being — and why does that matter for everything downstream, from this module through mapping?

02

Refresh: how Illumina sequencing works

✓ Complete
Concept

Just enough to make a FASTQ file meaningful, not a full chemistry lecture:

  • DNA is fragmented and ligated to adapters on both ends
  • Fragments bind to a flow cell and are locally amplified into clusters — many identical copies, needed so the optical signal is strong enough to detect
  • Sequencing by synthesis: fluorescently labelled bases are added cycle by cycle and imaged; each cycle reveals one position
  • For paired-end runs, after reading from one end the process re-primes and reads from the other end too (more on this in Exercise 6)
  • Each cycle's signal becomes a base call plus a confidence value — the Phred quality score
Task

In one sentence: why is a cluster of many identical copies needed, rather than sequencing one DNA molecule directly?

Check yourself

If the fluorescence signal at a given cycle is weak or ambiguous between two bases, would you expect the resulting Phred quality score to be high or low? Why?

03

What is a sequencing library?

✓ Complete
Concept

A library is a prepared, adapter-ligated, sequencer-ready collection of DNA molecules derived from a sample. A single specimen can genuinely yield several distinct libraries, for reasons including:

  • Multiple independent extractions or preparations
  • Different library protocols (e.g. single-stranded vs. double-stranded library chemistry, common in ancient DNA work)
  • Independent sequencing batches run at different times
  • Deliberate attempts to increase total sequencing depth
  • Resequencing

Don't assume which of these applies to any particular real dataset unless the metadata or publication actually says so — that's exactly what Exercise 8 will have you work out.

The real Great Auk genome project (ENA BioProject PRJNA1228327) consists of 13 separately named libraries — G1–G4, GH1–GH4, lib_12, lib_15, lib_20, lib2_13, lib2_17 — all from one specimen (BioSample SAMN47047800).

Task

Before Exercise 8 tries to pin this down carefully, write your own first-pass hypotheses: what are 2–3 plausible, genuine reasons a single historical specimen might have been prepared into 13 separate libraries rather than one?

Check yourself

Does a larger number of libraries automatically mean a larger number of individuals were sampled? Why is that assumption risky?

04

Specimen, sample, library, experiment, and run

✓ Complete
Concept

This distinction matters enough to be explicit, using ENA's own terms:

  • Specimen — the physical biological source (here: one museum-vouchered Great Auk)
  • Sample (ENA/NCBI BioSample, accession prefix SAMN/SAMEA) — the database record describing that specimen/extraction
  • Library (ENA experiment, prefix SRX/ERX) — one prepared, sequenceable DNA pool
  • Run (prefix SRR/ERR) — one actual execution of sequencing on a library, producing FASTQ file(s)

In general, this hierarchy can branch at more than one level — illustrated generically below (not real data):

Specimen
└── Sample / extraction
    ├── Library A
    │   ├── Run 1 → FASTQ
    │   └── Run 2 → FASTQ
    └── Library B
        └── Run 3 → FASTQ

Now compare that to the real Great Auk project, which turns out to be flatter than the generic picture above — every library here has exactly one run:

Specimen (NHMD153070)
└── Sample SAMN47047800
    ├── Library G1  → Run SRR32500060 → FASTQ
    ├── Library G2  → Run SRR32500059 → FASTQ
    ├── Library GH1 → Run SRR32500064 → FASTQ
    ├── …
    └── Library lib2_17 → Run SRR32500066 → FASTQ
        (13 libraries total, each with exactly one run)
Task

Match each ENA/NCBI accession prefix to the right level of the hierarchy: PRJNA, SAMN, SRX, SRR. Then, before checking in Exercise 7, say how many of each you'd expect to see for the Great Auk project.

Check yourself

"One specimen is not necessarily one library" and "one library is not necessarily one run" — which of these two statements does the real Great Auk data confirm, and which does it leave untested (because the data happens not to show that particular case)?

05

What is a FASTQ file?

✓ Complete
Concept

FASTQ represents each read as exactly four lines. Here's an illustrative example (not a real Great Auk read — you'll inspect real ones in Exercise 10):

1 · ID@SRR_EXAMPLE.1 1 length=101
2 · SequenceAGCTTAGCTAGCTACGGAATTCCCAGGACCTGATCGATCGATCGTAGCTAGCATCGATCGTAGCTAGCTAGCTAGCATCGTAGCTAGCATCGTAGCTAGC
3 · Separator+
4 · QualityAAFFFKKKKKKKKKKKKKKKKKKKKKKKKFFFKKKKKKKKKKKKKKKKKKKKKK:::::,,,,,,,,,,,,,,,,,,,,,,,,,,,,,,,,,,,,,,,,,,

Line 1 starts with @ and identifies the read. Line 2 is the called sequence. Line 3 is almost always a bare + (historically it could repeat the identifier). Line 4 is the same length as line 2 — one character per base — each character encoding a Phred quality score as an ASCII character (higher letters later in the ASCII range generally mean higher quality under the near-universal Phred+33 encoding). Real FASTQ files are almost always distributed as .fastq.gz.

Task

Using the example above, note in your own words which line is which. Then look at the quality line: does it stay constant across the read, or change? Where would you expect quality to be worst, and why?

Check yourself

If you opened a FASTQ file and every single quality character was identical, what would that suggest to you — ordinary real sequencing, or something worth double-checking (e.g. a placeholder or simulated file)?

06

Paired-end vs. single-end: what does this dataset actually use?

✓ Complete
Concept

In paired-end sequencing, a fragment is read from both ends, producing two files per run — R1 and R2. R1 and R2 are mates: the same physical fragment, observed from each end, not two independent reads. Read n in R1 must correspond to read n in R2 — pairing must stay synchronized. This is the common Illumina design, and you will likely meet paired-end data elsewhere in this project. But don't assume it applies here — check.

Task

Check the library_layout field for the Great Auk runs (ENA browser or the filereport API — you'll use both properly in Exercise 7). Is it PAIRED or SINGLE? What does that tell you about how many FASTQ files to expect per run?

Hint

A single field in the run metadata answers this directly — you don't need to infer it from file counts.

Show answer

All 13 Great Auk runs are library_layout: SINGLE — one FASTQ file per run, not an R1/R2 pair. A plausible (not confirmed) reason: ancient DNA fragments are frequently shorter than a single Illumina read. When that's true, reading both ends adds little — the two reads would mostly re-sequence the same bases or run past the fragment into adapter — so some ancient DNA projects sequence single-end instead. There's no publication linked to this project to confirm that this is the actual reason here, so treat it as a reasonable hypothesis, not a fact.

Check yourself

If this dataset were paired-end instead, what failure mode would you need to watch for that simply doesn't exist for single-end data?

Explore the actual Great Auk dataset on ENA

✓ Complete
Concept

You can browse ENA records through its web interface, but for anything you intend to record in a manifest, its filereport API is more reproducible than copying numbers off a webpage by hand — the same philosophy as downloading by accession in Module 01.

Task

Using the ENA browser page for PRJNA1228327 and the filereport API, build your own table recording: the BioProject and BioSample accessions, the specimen's voucher/locality/collection date, and for each of the 13 runs — run accession, experiment accession, library name, platform, layout, read count, base count, FASTQ file size, and MD5 checksum.

Hint

The filereport endpoint takes an accession and a comma-separated list of fields. Construct the URL yourself rather than guessing field names from memory — fields=run_accession,experiment_accession,library_name,library_layout,instrument_platform,read_count,base_count,fastq_ftp,fastq_md5,fastq_bytes is a good starting set.

Show command
curl -s 'https://www.ebi.ac.uk/ena/portal/api/filereport?accession=PRJNA1228327&result=read_run&fields=run_accession,experiment_accession,library_name,library_layout,instrument_platform,read_count,base_count,fastq_ftp,fastq_md5,fastq_bytes&format=tsv'

This prints a tab-separated table with one header row and one row per run — redirect it to a file (> ena_filereport.tsv) and use it directly, rather than retyping anything by hand. Record the result in your notes below.

09

Download the Great Auk reads from ENA

✓ Complete
Concept

Unlike NCBI's datasets tool in Module 01, ENA needs no special client at all — the filereport gives you direct HTTPS URLs and MD5 checksums, so wget plus md5sum is the whole toolchain. All 13 runs together total roughly 96.5 GB — too much to treat as a single step, and too much to just run on the login node as an ordinary transfer. Mjolnir's storage documentation draws exactly this distinction: everyday transfers ("a few files, actively working") belong on the login node, but a large, long-running transfer has its own dedicated filetransfer partition and QoS — the same one Module 00 mentioned existed without going into detail. It allows up to 4 days of runtime with 1 CPU and 20 GB memory, and is restricted to transfer commands specifically — "running compute work through it is a misuse."

Mjolnir explicitly documents this partition/QoS for transfer commands such as rsync, scp, and sftp — it does not list wget by name. Using wget here is our reasonable extension of that documented transfer pattern — it is a plain network-transfer command, not compute — rather than an example shown verbatim in the documentation. Worth knowing if you ever need to justify it.

Task

Stage 1 — on the login node, download the smallest run (SRR32500061, library GH4, ~1.6 GB) into its own subdirectory, and verify it against its MD5. Stage 2 — use your saved filereport TSV from Exercise 7 to build a script that loops over all 13 runs, giving each its own subdirectory, without concatenating anything. Stage 3 — wrap that script as a Slurm batch job using the filetransfer partition/QoS. Stage 4 — submit it with sbatch so the full download runs independently while you continue with later exercises.

Hint

The fastq_ftp field from ENA is given without a URL scheme — you need to prepend https:// yourself. The filetransfer QoS needs its own #SBATCH directives, the same pattern you wrote in Module 00 — just with --partition=filetransfer --qos=filetransfer in place of cpuqueue/normal.

Show command
# Stage 1 — smallest run first, by hand, on the login node (ordinary transfer) mkdir -p raw_reads/great_auk/SRR32500061 cd raw_reads/great_auk/SRR32500061 wget https://ftp.sra.ebi.ac.uk/vol1/fastq/SRR325/061/SRR32500061/SRR32500061.fastq.gz echo '1172900a7bc06532a413ab4df56ee794 SRR32500061.fastq.gz' | md5sum -c - cd ../../../ # Stage 2 — build the full loop from your saved filereport TSV cat > download_all.sh <<'EOF' #!/bin/bash tail -n +2 metadata/ena_filereport.tsv | while IFS=$'\t' read -r run exp lib layout plat rc bc url md5 bytes; do mkdir -p raw_reads/great_auk/$run wget -q -O raw_reads/great_auk/$run/$(basename $url) https://$url echo $md5 raw_reads/great_auk/$run/$(basename $url) | md5sum -c - done EOF # Stage 3 — wrap it for Mjolnir's dedicated large-transfer QoS (max 4 days, 1 CPU, 20GB — transfer only) cat > download_all.sbatch <<'EOF' #!/bin/bash #SBATCH --job-name=great_auk_download #SBATCH --partition=filetransfer #SBATCH --qos=filetransfer #SBATCH --cpus-per-task=1 #SBATCH --mem=20G #SBATCH --time=1-00:00:00 #SBATCH --output=raw_reads/great_auk/download-%j.out #SBATCH --error=raw_reads/great_auk/download-%j.err bash download_all.sh EOF # Stage 4 — submit, rather than running the full download directly on the login node sbatch download_all.sbatch

Adjust the read -r variable list if you requested a different field order in Exercise 7 — the names must line up with your TSV's actual column order.

Organise and verify the raw data

✓ Complete
Concept

Module 01 already created an empty raw_reads/ directory alongside reference_genomes/ — this is where it finally gets used. Verification should be streaming and safe: checking a 27 GB file shouldn't require fully decompressing it onto disk.

Task

Hint

Show command
ls -lh raw_reads/great_auk/*/ for f in raw_reads/great_auk/*/*.fastq.gz; do gzip -t "$f" && echo "OK: $f"; done zcat raw_reads/great_auk/SRR32500061/SRR32500061.fastq.gz | head -n 8
