Reference Genome

Every comparative genomics project starts from a reference: a published genome assembly that downstream reads are compared against. Before you align a single read, you need to know what reference you're using, where it came from, and whether it's actually appropriate for this project. This module is about doing that carefully, on Mjolnir (the University of Copenhagen's HPC cluster), using the same basic commands and HPC habits you'll rely on for the rest of the project.

Learning objectives

  • Confidently orient yourself on Mjolnir and the filesystem (pwd, ls, cd)
  • Understand the difference between Mjolnir's login and compute nodes, and where project files should live
  • Create a sensible, well-named project directory structure in the right location
  • Explain the difference between an absolute and a relative path
  • Identify a genome assembly that is appropriate as a reference for this project
  • Download a file from a public genomic database onto the server
  • Inspect a file without fully opening it: size, type, and compression state
  • Read and interpret FASTA format, including headers
  • Record what you downloaded, from where, and why — your first lab notebook entry

01

Orient yourself on the server

✓ Complete
Concept

You'll be doing this project's practical work on Mjolnir, the University of Copenhagen's HPC cluster. Logging in doesn't put you on the machine that actually runs analyses — it puts you on a login node, a shared entry point used by everyone connected at that moment. Login nodes are for lightweight tasks: organising files, writing scripts, submitting jobs. Running real computation there slows down every other user's session, and persistent misuse can lead to your access being withdrawn. Actual analyses run on compute nodes, scheduled through Slurm — you'll meet that properly in a later module. For now, the habit to build is simple: before you create or download anything, know where you are — both in the filesystem, and on which kind of node.

Task

Connect to Mjolnir over the UCPH VPN, then log in over SSH with your KU ID. Once connected, confirm two things: (a) which machine you've landed on, and (b) your current working directory and what's already inside it.

Hint

One command prints the hostname of the machine you're on — on Mjolnir this confirms you're on a login node. Two more commands tell you where you are and what's there (you'll recognise these from general Linux use).

Show command
# from your own computer, with the UCPH VPN connected ssh <KU-ID>@mjolnirgate.unicph.domain # once logged in hostname pwd ls -lh

hostname prints the name of the machine you're currently on — useful for confirming you've landed on a login node rather than assuming it. pwd (print working directory) prints the absolute path of where you are. ls -lh lists the contents of that directory with human-readable file sizes.

Check yourself

Does pwd show you're in your home directory by default? What does that tell you about where you should (and shouldn't) store this project's data — see Exercise 2.

02

Create a project directory

✓ Complete
Concept

On a shared HPC system, you don't just create directories wherever you like — the system has designated locations, and using the wrong one has real consequences. Your home directory on Mjolnir (/home/<KU-ID>) is personal but capped at 100 GB, and is meant for configuration files and small scripts — not datasets or analysis output; filling it can make your jobs fail later on. Actual project data belongs under /projects/<project>/, which already has a standard internal layout, including a people/<KU-ID>/ directory that is your own working space within the project. If that folder doesn't exist for you yet, the right move is to ask your supervisor or Mjolnir support to have it created — not to improvise one yourself elsewhere.

Task

Navigate to your personal working directory within the project's shared space, and create one subdirectory there for this specific Great Auk project — something to keep it separate from any other work you might do inside the same personal folder.

Hint

The path has the shape /projects/<project>/people/<KU-ID>/ — ask your supervisor for the actual project name if you don't have it yet. Give your new directory a short, clear, lowercase name with no spaces.

Show command
# replace <project> and <KU-ID> with your actual values cd /projects/<project>/people/<KU-ID>/ mkdir great_auk

mkdir (make directory) creates a new, empty directory with the name you give it. This project directory's exact name is up to you — great_auk is just an example.

Check yourself

Run ls and pwd again. Is your new directory there, and does the absolute path start with /projects/ rather than /home/? Why does that distinction matter here?

03

Create a directory for reference genomes

✓ Complete
Concept

Good directory organisation means each type of data gets its own clearly labelled place. Reference genome files are logically distinct from raw sequencing reads, which are distinct from results. Separating them now, before you have any files, is far easier than reorganising later.

Task

Inside your project directory, create a subdirectory to hold reference genome files. Choose a name that would make sense to someone else looking at your project for the first time.

Hint

mkdir can take a path, not just a bare name — it doesn't have to be run from inside the parent directory first.

Show command
mkdir great_auk/reference_genomes

A name like reference_genomes is immediately understandable. Avoid vague names like data or stuff — they tell a reader nothing.

Check yourself

Use ls on your project directory. Does it show the new subdirectory? How might you list the contents of the project directory and its subdirectories in one go?

05

Absolute versus relative paths

✓ Complete
Concept

An absolute path describes a location starting from the root of the filesystem (/) — it is unambiguous no matter where you currently are. A relative path describes a location relative to your current working directory — short and convenient, but it only means what you think it means if you know where you're starting from. Mixing these up is one of the most common sources of "file not found" errors and, worse, scripts that silently do the wrong thing.

Task

From inside reference_genomes, write down (in your notes) both the absolute path and a relative path (relative to your project directory) that point to the same location. Then test both: use each path with cd to confirm they take you to the same place.

Hint

An absolute path always starts with /. A relative path never does. cd .. and cd ../.. move up one and two levels respectively, using relative notation.

Show command
# absolute path (use the real path reported by your own pwd) pwd cd /projects/<project>/people/<KU-ID>/great_auk/reference_genomes # relative path, from the great_auk project directory cd ../reference_genomes

Replace <project> and <KU-ID> with the actual path reported by pwd on your system.

Check yourself

If you changed your current directory first, would the relative path you wrote down still point to the same place? Why or why not?

06

What is a reference genome, and where do you find one?

✓ Complete
Concept

A genome assembly is a reconstruction of an organism's genome built from sequencing data — overlapping reads are computationally joined into longer stretches of contiguous sequence (contigs), which may themselves be ordered and joined into larger scaffolds, and ideally into full chromosomes. A reference genome is simply an assembly chosen to serve as the standard coordinate system that other data (reads, variants, annotations) get compared against.

Not every assembly is equally useful as a reference. Assembly quality varies enormously — from highly fragmented draft assemblies with thousands of short scaffolds, to chromosome-level assemblies with a handful of large, well-ordered sequences. For a species as rare as the Great Auk (Pinguinus impennis, extinct since the mid-19th century), a reference assembled directly from its own genome may not exist or may be limited; in that case, a high-quality assembly from a closely related living species can serve as a reference instead — the Alcidae family (auks, murres, puffins, razorbills) includes several extant species useful for this kind of comparative work.

Task

Using NCBI Datasets and/or the ENA browser (see Genome Resources), search for genome assemblies for Pinguinus impennis and for relevant living relatives. For each candidate you find, record in your notes: the organism name, the assembly accession, the assembly level (contig / scaffold / chromosome), and the submitting institution or project. Do not download anything yet — this step is purely about identifying candidates.

Hint

On the NCBI Datasets genome page, searching by organism name will show you an assembly level column directly in the results table — this is the fastest way to compare multiple candidates at a glance.

Show solution approach

There is no single command here — this is a research task. A reasonable approach:

  1. Search NCBI Datasets (Genomes) for "Pinguinus impennis".
  2. Note whether any assembly exists, and if so its accession and assembly level.
  3. Search for one or two of the closest living relatives in Alcidae and repeat.
  4. Bring your shortlist to your supervisor before deciding which assembly to actually use as the project's reference — this is a scientific decision, not just a technical one.

This website does not prescribe a specific accession — the correct choice depends on decisions you'll make together with your supervisor.

Check yourself

Can you explain, in your own words, why a chromosome-level assembly is generally preferable to a highly fragmented one for comparative genomics? What might you lose by using a more fragmented assembly?

07

Download the reference FASTA

✓ Complete
Concept

Once an assembly has been agreed with your supervisor, you need to get the actual sequence file — typically a FASTA file — from the database onto the server. Command-line download tools let you pull files directly onto a remote server without downloading to your laptop first and re-uploading, which matters once files get large.

A single reference genome download is a lightweight, network-bound task, so doing it directly on the Mjolnir login node (as in Exercise 1) is appropriate — this is the kind of file organisation and preparation work login nodes are for. The judgement call to keep practising: if a step starts taking a long time or using significant CPU or memory (for example, decompressing a very large file), that's a signal it belongs on a compute node instead, not the login node.

Task

Once you and your supervisor have confirmed which assembly to use, find its download link (NCBI Datasets and ENA both provide direct FASTA download links on the assembly page), and download it into your reference_genomes directory using wget or curl. Give the downloaded file a meaningful name if the default filename isn't clear.

Hint

wget <url> downloads a file keeping its original name. curl -L -o <filename> <url> downloads it under a name you choose (-L follows redirects, which genomic databases often use).

Show command
# option A — keep the server's original filename wget <DOWNLOAD_URL> # option B — choose your own filename curl -L -o great_auk_reference_genomic.fna.gz <DOWNLOAD_URL>

Replace <DOWNLOAD_URL> with the actual link from NCBI Datasets / ENA for the assembly you and your supervisor selected. If wget isn't available on your server, use curl.

Check yourself

Did the download finish without errors? What does the tool's output tell you about the file size it expected versus what it actually received?

08

Inspect the downloaded file

✓ Complete
Concept

Never assume a download worked correctly just because the command finished. A silently truncated or corrupted file will cause confusing errors much later, often far from the actual cause. A quick inspection immediately after downloading is cheap insurance.

Task

List the contents of your reference_genomes directory and note the exact filename and size of what you downloaded.

Hint

You already used this command in Exercise 1 — the -h flag makes file sizes human-readable (KB/MB/GB) instead of raw byte counts.

Show command
ls -lh
Check yourself

Does the file size look reasonable for a genome assembly (typically tens of megabytes to a few gigabytes, depending on genome size and compression)? A file of only a few kilobytes usually means something went wrong.

09

Understanding compressed (.gz) files

✓ Complete
Concept

Genomic files are large and highly compressible, so they are almost always distributed compressed — most commonly with gzip, giving a .gz extension (e.g. genome.fna.gz). A .gz file is a compressed version of the original; the original filename is normally everything before the .gz. Many bioinformatics tools can actually read gzip-compressed files directly, so decompression is not always required — but you need to be able to recognise and handle compression either way.

Task

Confirm that your downloaded file is indeed gzip-compressed, without decompressing it yet. Use its file extension as a first clue, then confirm using a command that inspects file content rather than just the name.

Hint

File extensions are just a naming convention — they can be wrong or missing. One command actually examines the file's contents to determine its real type.

Show command
# replace with your actual filename file <your_downloaded_file>

file inspects the actual bytes of a file and reports its real type, regardless of what the extension claims.

Check yourself

Does the output of file mention "gzip compressed data"? What would it say instead if the file were plain text?

10

Decompressing the file

✓ Complete
Concept

For this early inspection stage, it's useful to have an uncompressed copy so you can look directly at the FASTA content with simple tools. Later in the project, once files get much larger, you'll often keep data compressed and use tools that read .gz files directly to save disk space — but for now, decompressing is the simpler option while you're learning to read FASTA format.

Task

Decompress your downloaded .gz file. Decide (and note down your reasoning) whether you want to keep the original compressed file as well.

Hint

By default, the standard decompression command removes the .gz file once it's done. A flag exists if you want to keep both the compressed and decompressed versions.

Show command
# this replaces the .gz file with the decompressed version gunzip <your_file>.gz # -k ("keep") preserves the original .gz file as well gunzip -k <your_file>.gz
Check yourself

Run ls -lh again. How does the uncompressed file's size compare to the compressed version? Does that match your expectation for genomic sequence data?

11

Check file size and file type

✓ Complete
Concept

With the uncompressed file in hand, it's worth re-confirming both its size and its type — this time you should be looking at plain text, not compressed binary data. This habit of "trust but verify" after every transformation will save you a lot of debugging time over the course of the project.

On Mjolnir, /projects/ storage isn't currently quota-limited the way your home directory is — but it's still a shared, finite resource used by many research groups, not an unlimited personal allocation. Checking usage with du periodically, as you're doing here, is good practice rather than a one-off exercise.

Task

Check the size and type of the decompressed file, and also check how much disk space your whole reference_genomes directory is now using.

Hint

You've used two of these commands already. The third, du (disk usage), summarises space used by files or directories — the -h and -s flags make the output short and readable.

Show command
ls -lh file <your_file> du -sh .
Check yourself

Does file now report something like "ASCII text" rather than "gzip compressed data"? Does du -sh . roughly match what you'd expect from adding up the files you can see?

12

Inspect the beginning of the FASTA file

✓ Complete
Concept

Genome FASTA files can be enormous — opening one fully in a text editor is slow at best and can freeze your session at worst. Instead, you look at just the first portion to confirm the file looks as expected, using a tool designed for exactly this.

Task

Print the first 20 lines of your decompressed FASTA file to the screen.

Hint

One command prints the "head" (start) of a file. It takes a flag to control how many lines are shown.

Show command
head -n 20 <your_file>

For scrolling through more of the file interactively (rather than a fixed number of lines), less <your_file> lets you page through and search — press q to quit. See the Terminal Toolbox for more on less.

Check yourself

Does the very first line start with a > character? What do you think everything after that line, up until the next >, represents?

13

Understanding FASTA headers

✓ Complete
Concept

FASTA format represents one or more sequences as: a header line starting with >, followed by the sequence itself (usually wrapped across multiple lines, often 60 or 70 characters wide). The header typically contains a sequence identifier and, often, free-text description — for a genome assembly, headers usually identify each contig, scaffold, or chromosome. An assembly with hundreds of thousands of headers is a sign of a fragmented assembly; one with a small number of headers matching the expected chromosome count is a sign of a chromosome-level assembly.

Task

Count how many sequence headers are in your FASTA file (i.e. how many individual sequences — contigs, scaffolds, or chromosomes — it contains). Then look closely at a few header lines and note what information they contain.

Hint

You can search for lines matching a pattern with grep, and count matching lines with the -c flag. The pattern you want matches lines starting with >.

Show command
grep -c '^>' <your_file> grep '^>' <your_file> | head -n 5

The first command counts all lines starting with > — i.e. the number of sequences in the file. The second extracts all header lines and pipes them into head so you only see the first five.

Check yourself

Does the number of headers roughly match what you'd expect for the assembly level you recorded in Exercise 6 (e.g. close to the known chromosome count for a chromosome-level assembly, or a much larger number for a scaffold-level one)?

14

Identify important assembly metadata

✓ Complete
Concept

The FASTA file itself only contains sequence and minimal header text. The full context — assembly accession and version, assembly name, submitting organisation, sequencing technology used, assembly date, total assembly length, number of chromosomes/scaffolds, and BUSCO or other quality metrics — normally lives on the database's assembly report page, not inside the FASTA file. Recording this metadata alongside the file is essential: a bare file called genome.fna tells a future reader (including future you) nothing about its provenance.

Task

Go back to the database page for the assembly you downloaded (NCBI Datasets or ENA) and record its key metadata: assembly accession, assembly name, assembly level, total assembly length, number of sequences, and submitter/organisation.

Hint

On NCBI Datasets, this information is typically summarised in a table on the assembly's overview page — you generally don't need to calculate it yourself from the FASTA file.

Show solution approach

There's no single command for this — it's a matter of reading the database page carefully. A useful habit: copy the metadata table (or a screenshot/link to it) directly into your notes below, so you don't have to re-find the page later.

Check yourself

Does the total assembly length roughly match what you'd expect from the uncompressed file size you measured in Exercise 11 (allowing for the fact that each base is one character, plus header lines and line breaks)?
